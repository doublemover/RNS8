# RNS8 source and qualification audit — 2026-10-06

## Result

The source-preparation work is complete; **GPU qualification is not**. This
revision repairs active correctness defects, removes unsafe or unreachable
prototype paths, adds CPU and hardware regressions, provides an executable
qualification manifest, and replaces conflicting completion claims with current
contracts and gates. No HIP compiler, GPU execution, performance campaign, paid
compute, remote publication, or user-computer access was used for this audit.

The starting tree was GitHub `main` at
[`80791bd3d2900bd80b2ac6ba957d15329771043a`](https://github.com/doublemover/RNS8/commit/80791bd3d2900bd80b2ac6ba957d15329771043a).
The checkout was clean. Remote `codex/perf-queue-control-panel` and recent merge /
optimization history were inspected; its divergent work was not overwritten or
silently merged. Historical documents were retained under `docs/archive/`.

This is an extended source audit and tested repair slice, not a formal proof of
the entire library. The distinction between active dispatch, dead candidates,
source coverage, host arithmetic, and actual hardware evidence is intentional.

## Findings and disposition

Old file/line references below are relative to the exact starting commit above;
they remain recoverable with `git show 80791bd:<path>`. New references name the
retained implementation or regression in this checkout.

### F01 — Active short-prefix CRT overflows uint64 (critical)

**Old:** `src/backend_hip_direct/hip_direct_export_kernels.cuh:1646–1660`,
`hip_direct_device_common.cuh:9–25`, and
`hip_backend_export_bounded.inc:58–80,372–391`.

The precomputed CRT weights themselves are correct. The expression
`(acc + canonical * weight) % P` first wraps in uint64. Prefix 8's product fits
uint64, but its weighted terms do not. With the default first eight moduli,
reconstructing the integer **2 produces 4558134011519499778** in that arithmetic.
The bounded signed/unsigned export dispatcher actively selected these kernels.

**Repair:** remove the duplicate weighted-CRT path and route all bounded prefixes
through the existing three-limb incremental Garner implementation. This sacrifices
an unqualified optimization rather than attempting a new unmeasured arithmetic
shortcut. `test_hip_arithmetic_host.cpp` executes the actual scalar wide helper
against Boost for every supported prefix; GPU export tests include `x=2` at
prefix 8. Full hardware compilation/execution remains pending.

Standalone reproduction of the old expression:

```python
from math import prod
moduli = [256, 255, 253, 251, 247, 239, 233, 229]
P = prod(moduli)
mask = (1 << 64) - 1
acc = 0
for m in moduli:
    weight = (P // m) * pow(P // m, -1, m) % P
    acc = ((acc + (2 % m) * weight) & mask) % P
assert acc == 4558134011519499778  # mathematically correct answer: 2
```

### F02 — Active bounded status elision can return stale output (critical)

**Old:** `hip_backend_export_bounded.inc:35,343`; the generic cell exporters in
`hip_direct_export_kernels.cuh:139–176` return early on a range error.

For every prefix ≥9, the host wrapper stopped allocating/reading status and
passed null. An out-of-bound representative made the kernel return without
writing that cell; the host wrapper then copied the staging buffer and returned
success. Prefix width does not prove that a caller-supplied bound is met.

**Repair:** bounded exports always clear, pass and read the range-status buffer
before committing output. Retain valid exact-wide width-proven elision and
all-zero schedule handling as separate policies. New GPU tests check each failing
position in a 65-cell output at prefixes 1/7/8/9/20, repeated exports and padding
against CPU preservation semantics. Export metadata already required checked
status; the implementation now matches it.

### F03 — Active persistent small GEMM does not reduce between K blocks (high)

**Old:** `hip_direct_gemm_kernels.cuh:33–49`, dispatched by
`hip_backend_gemm_rns.inc:137–146` for compact output area ≤64.

The code chunked loop indices at 65536 but accumulated all chunks into one
int32. For valid centered residues such as -127, sufficiently long K overflows.
The compact path also failed to require `ldc == n`, although its kernel ignored
output stride.

**Repair:** use a shared host/device blocked residue dot helper, resetting the
int32 sum and reducing with a centered carry after each safe block. Require
compact A, B **and C** strides before that dispatch. CPU regression coverage
spans all 20 supported moduli and K through 262145, with padded B stride and
alternating/nonalternating data. GPU persistent tests exercise the same K edges.

### F04 — Active four-cell packing skips plane starts (high)

**Old:** `hip_direct_pack_kernels.cuh:969–1000`; dispatcher selects this path for
contiguous 256–4096-cell signed inputs.

One plane was chosen for a four-output group, then the loop broke at its end.
When the plane length was not divisible by four, the next group's start skipped
the first outputs of the next plane. For 257 cells, outputs 257–259 were skipped.

**Repair:** resolve plane and element for every output lane. The host-only test
executes this actual scalar kernel body at 255/256/257/258/259/4095/4096 cells,
full-width native values and prefixes 1/8/9/20; the GPU differential adds padded
strides and the >4096 dispatch boundary. Comments no longer claim a vector load
or a single memory transaction that the scalar source does not implement.

### F05 — Active AMDGPU skinny dispatch violates finite and wave contracts (critical)

**Old:** `src/backend_amdgpu_builtins/amdgpu_builtins_kernels.hip:739–770,1121–1245`.

The "WMMA skinny" kernels contained scalar multiply/shuffle loops, not WMMA.
They treated `plane_count_or_modulus` as a prefix even in `Finite=true` dispatch,
so a finite modulus such as 251 caused access to nonexistent residue planes.
They ignored strides, looped over every plane despite grid.z, and assumed
64-thread cross-lane reduction on an RDNA3 wave32 route. The 256-thread mapping
also mixed output columns and did not cover them as its launch implied.

**Repair:** remove these candidates and restore the existing
`rdna3_dense_wmma_kernel<Finite>` for all dense RDNA3 widths. The real kernel uses
separate finite/RNS template semantics and the supplied strides. Expand its
finite CPU differential to N=1/2/4/5/8/19. Widen common builtins load/store
address products to int64 so large plane/row offsets do not overflow int32.
The wider offsets and restored kernel still require on-device validation.
AMD's [HIP porting guidance](https://rocmdocs.amd.com/projects/HIP/en/latest/how-to/hip_porting_guide.html)
also warns against assuming one wave size across RDNA/CDNA targets.

### F06 — Dead export/native prototypes are unsafe (high if enabled)

**Old:** `hip_direct_export_kernels.cuh:1304–1642`,
`hip_direct_gemm_kernels.cuh:54–88`, and appended wrappers in `hip_direct_kernels.hip`.

These had no public caller in the audited tree:

- DPP status aggregation shuffled the original status at each XOR offset rather
  than the accumulated result. A failure at lane 3 need not reach writer lane 0.
- Combined signed export passed null status with checking enabled.
- Fused GEMM/export used a wrapped prefix-9 product with at most eight planes,
  ignored strides, and retained the same unreset K accumulator.
- Native signed GEMM could overflow signed int64 and clamped a range failure to
  zero without returning an error.

**Disposition:** remove the dead wrappers/kernels and unused metadata identities.
No public feature is claimed lost. Safe fused reconstruction and measured small-N
optimization remain research requirements in the specification/roadmap.

### F07 — Wrap64 prototypes and dispatch claims diverge (high/medium)

**Old:** `src/backend_wrap64/wrap64_hip_kernels.hip:624–757`,
`wrap64_hip.cpp:263–278,347–438`.

The uncalled fused-v5 kernel read single bytes rather than each element's eight
limbs, used K to invent diagonal positions, and included a shift by 64. Its table
and DPP helper were unused. A graph prototype was nested inside the HIP-disabled
branch and another HIP-enabled conditional, making it unreachable in every build.
Separately, the active ≥1024 shape override forced the u64 tiled kernel while
shared metadata still advertised the K-based u32/colpair selection.

**Repair:** remove uncalled v5/graph/table helpers and restore the existing shared
K/shape dispatcher for live wrap64 execution. The established byte-GEMM36 tiled
u32/u64 and explicitly enabled colpair experiment remain. Existing CPU exhaustive
byte-pair/carry tests and HIP wrap differentials remain; no new speed claim is made.

### F08 — Dead planning/packing/grouping code falsely implied capabilities

**Old:** `src/core/plan_lowering.cpp:9–32,150–166`,
`api_plan_schedule.inc:2–33`, appended graph helpers in
`hip_backend_gemm_rns.inc:609–693` and `hip_backend_gemm_finite_tiled.inc:731–779`,
plus AMDGPU "WMMA-native pack" wrappers.

The unused min-prefix helper overflowed both `2*bound` and its modulus product;
the actual planner already uses Boost. The "adversarial detector" neither
examined inputs nor controlled safe accumulation. Modulus-family classification
was unused. Duplicate graph prototypes had no API caller; the bounded one would
have treated each plane as modulus-index zero. The extra grouped-finite "GEMM"
only exported residues. WMMA-native pack helpers neither uploaded host inputs as
claimed nor transformed a WMMA-specific layout, and were uncalled.

**Disposition:** remove these helpers, dead INT4 packing and contradictory
research declarations, while retaining the real planner, resident/grouped APIs,
benchmark graph implementation, and future design requirements. The INT4 pack
had no valid CRT/finite arithmetic contract and inconsistent declarations; no
working INT4 backend was removed.

### F09 — Reserved research APIs documented nonexistent behavior

**Old:** `include/rns8/semantics.h:17–23`, `include/rns8/rns8.h:1230–1280`, and
`src/core/api_gemm.cpp:1500–1541`.

Ozaki, Strassen and Freivalds entrypoints always return unsupported. The headers
claimed enabling flags and a probabilistic result status that do not exist.

**Repair:** preserve numeric enum values and exported reserved entrypoints,
but document them as unimplemented and test that they leave outputs unchanged.
No default exact API uses these research methods. Ozaki/FP8 comparisons in the
research material remain possible future work, not an implementation assertion.

### F10 — Malformed C/FFI enums triggered UB before rejection (high)

The initial UBSan run failed in five invalid-descriptor tests because loading
out-of-range values through unfixed C++ enum types is undefined behavior. Tests
that expect invalid values to be rejected should not require disabling UBSan's
enum checks.

**Repair:** introduce `rns8/abi.h` and explicitly back public C++ enums with
uint32. C headers retain normal enum syntax. All enum/struct sizes and alignments
were compared before/after in GCC C11 and C++17 and were identical; static tests
pin every public enum to 32-bit storage. Existing malformed-value tests now pass
under UBSan. Supported C callers must use the normal 32-bit enum ABI, not
`-fshort-enums`. MSVC/Windows ABI and downstream checks remain a hardware-host gate.

### F11 — Validation and evidence tooling could hide drift (medium)

- Correct stale export-report fixtures that used a GEMM identity as an export
  identity and disagreed with backend metadata. Keep schema checks strict.
- Give downstream install tests isolated per-build directories and propagate

- Add flushed stage/count/elapsed progress and ten-second heartbeats to the

- Replace the dashboard's unvalidated "schema-valid" count and shape-only winner
  grouping with a schema-checked per-capture explorer. Escape displayed inputs,

  old HTML as an explicitly historical snapshot.

## Mathematical and architectural review

The retained CPU/reference design correctly separates bounded CRT, exact-wide,
finite-ring/field, and strict wrap64 contracts. Prefix selection uses
multiprecision products and strict inequalities. Tests establish the 28-value
ladder's pairwise coprimality and the supported 20-prefix range.

Exact-wide plan validation proves enough range for full native 64-bit input
products at the declared K. It does not promise an unlimited number of bits or
an arbitrary-depth residue-chain proof. Bounded output bounds and zero masks are
trusted caller metadata; aliasing under a false bound cannot always be detected
by an export check. These limits are now explicit in the README/correctness page.

The live graph implementation is benchmark-owned and distinct from removed dead
prototypes. AUTO uses reviewed exact-key entries, not unrestricted runtime tuning.
Source capability flags and registered kernel names are not hardware certificates.
The manifest inventories every retained `__global__` definition, while the
remaining qualification checklist requires concrete specialization/dispatch/ISA
coverage on each target.

## Remaining decisions and risks

1. Run the prepared direct-HIP qualification lane on each target, then optional
   accelerators. Treat any required skip, wrong target, compile failure or exact
   mismatch as a blocker, not a successful fallback.
2. Decide whether to reintroduce short-prefix CRT or skinny kernels only after a
   correctness proof, comprehensive regressions and hardware measurements. Their
   removal may change performance; no speed regression estimate is available.
3. Requalify actual DP4A signedness, WMMA/MFMA lane layout, sparse-A metadata,
   optional-library version behavior, and graph capture/lifetime legality.
4. Establish explicit range propagation or rejection rules for arbitrary-depth
   exact-wide residue chains before expanding that public guarantee.
5. Review very large dimensions/address arithmetic, allocation failures, and
   cross-device ownership with dedicated stress tests. This audit widened common
   builtins offsets but did not prove every kernel for every int64 descriptor.
6. Run LeakSanitizer on a compatible host and repeat C/FFI layout and package tests
   with the Windows toolchain. CPU scalar execution does not validate GPU races.
7. Archive new raw evidence with exact build provenance, then review performance
   and reinstall only justified cache entries. Old summaries alone cannot close
   these gates.
